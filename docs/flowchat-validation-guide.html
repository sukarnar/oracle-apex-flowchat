FlowChat developer guide

Business rules and validation with data sources

How FlowChat checks a change before it writes to your tables, what each check is for, and where to put your own rules.

Package FC_DATA · FC_ENGINENodes findRecord · changeFields · saveChanges · bulkUpdateAPEX 23.2 · Oracle 26ai

01The checkpoints

A record is edited in three steps. Find record loads it, Change fields lets the user edit fields one at a time, and Save changes writes them. Each step has its own checks, and Save changes runs the earlier ones again because a conversation can last a long time.

All checks run on the server inside FC_ENGINE and FC_DATA. The widget only displays prompts and sends answers, so nothing the browser sends can skip a rule.

  1. While the user answers
  2. 1Input rulesType, range, length, allowed optionsfield.input
  3. 2ValidatorsRegex patterns and server connectorsfield.validators
  4. 3Editable checkField whitelist plus the record's stateFC_DATA_SOURCE_FIELDS.UPDATABLE, editableWhen
  5. On every search, read and write
  6. 4Row filterWhich rows this user may see or changeFC_DATA_SOURCES.ROW_FILTER
  7. When Save changes runs
  8. 5Checks 1 to 3 againEach changed field, against the current answersrun_save
  9. 6Version checkNobody else saved the row in the meantimeVERSION_COLUMN or original values
  10. 7Your code and the databasePL/SQL source, constraints, triggersUPDATE_TARGET, DDL

Checks 1 to 3 give quick feedback while the user types. Checks 4 to 7 protect the data. A rule that matters to the business belongs in the second group, and can be repeated in the first for a better conversation.

02Register the data source

Flows refer to a data source by its id only. The table, its columns and its filter live in two tables that only administrators maintain, so a flow author can't point a flow at another table or widen what it may change.

ColumnUse for validation
SOURCE_TYPETABLE: FC_DATA writes the SQL from the registered columns. PLSQL: your functions do the search, read and update.
VERSION_COLUMNA number column FC_DATA increases by 1 on every save. It drives the concurrent edit check.
ROW_FILTERSQL added to every search, read and update as and (…). It may use :APP_USER and :FC_VERIFIED.
UPDATE_TARGETFor PLSQL sources, the function that saves a change.
FIELDS.UPDATABLEY on each field a flow may change. The default is N.
FIELDS.MASKlast4 shows only the last four characters in cards.

Example: loan applications a customer may edit while they are pending

insert into fc_data_sources (source_id, source_type, object_name, key_column, version_column, row_filter, description)
values ('loan_app', 'TABLE', 'LOAN_APPLICATIONS', 'APP_ID', 'ROW_VERSION',
        'customer_email = lower(:FC_VERIFIED)',
        'Loan applications, limited to the verified customer');

insert into fc_data_source_fields (source_id, field, column_name, data_type, label, searchable, updatable)
select 'loan_app', 'app_id',  'APP_ID',      'VARCHAR2', 'Reference',  'Y', 'N' from dual union all
select 'loan_app', 'status',  'STATUS',      'VARCHAR2', 'Status',     'N', 'N' from dual union all
select 'loan_app', 'amount',  'AMOUNT',      'NUMBER',   'Amount',     'N', 'Y' from dual union all
select 'loan_app', 'term',    'TERM_MONTHS', 'NUMBER',   'Term',       'N', 'Y' from dual union all
select 'loan_app', 'income',  'ANNUAL_INCOME', 'NUMBER', 'Income',     'N', 'Y' from dual;

Status and reference are readable but not updatable, so no flow can change them, whatever its JSON says.

03Input rules

Each field in a Change fields node takes the same input object as an Ask node. The engine parses the answer into the right type before anything else sees it, so a validator or your PL/SQL always receives a real number or an ISO date, never free text.

kindRules you can set
numbermin, max, with minMessage and maxMessage
dateminDate, maxDate (absolute, or relative such as today)
text, emailrequired, minLength, maxLength
choice, yesnooptions, static or from a list of values
{ "id": "edit_app", "type": "changeFields", "record": "app", "done": "review",
  "fields": [
    { "field": "amount", "label": "Amount",
      "input": { "kind": "number", "min": 1000, "max": 500000,
                 "maxMessage": "The most we lend is $500,000." } },
    { "field": "term", "label": "Term",
      "input": { "kind": "choice", "options": ["12", "24", "36", "60"] } }
  ] }

When a rule fails, the user sees the message and is asked for the same field again. Nothing is stored.

04Validators

A field can list validators, which run in order after the input rules pass. The first failure stops the list.

Pattern

{ "type": "regex", "pattern": "^\\+?[0-9 ]{8,15}$", "message": "Please enter a phone number with 8 to 15 digits." }

Server check

A server validator calls a connector. Use it for any rule that needs other answers or data: cross-field limits, duplicate checks, credit rules.

{ "type": "server", "connector": "check_affordability",
  "message": "That amount isn't available." }

The connector receives the standard payload plus the field being checked:

{ "sessionId": "…", "flowId": "loan_edit", "nodeId": "edit_app",
  "slot": "app.amount", "value": 250000,
  "slots": { … the conversation's answers … },
  "appUser": "JSMITH", "context": { … page context, if any … } }

It returns {"valid": true}, or {"valid": false, "message": "…"}. Its message wins over the one in the flow, so the rule's owner controls the wording.

Connector: amount at most five times annual income

create or replace function check_affordability (p_payload in clob) return clob is
  l_in     json_object_t := json_object_t.parse(p_payload);
  l_amount number        := l_in.get_number('value');
  l_income number;
  l_out    json_object_t := json_object_t();
begin
  -- the value being checked is the new amount; income is read from the table by the record key slot
  select annual_income into l_income
    from loan_applications
   where app_id = l_in.get_object('slots').get_string('app_ref');

  if l_amount > 5 * l_income then
    l_out.put('valid', false);
    l_out.put('message', 'We can lend up to ' || to_char(5 * l_income, 'FM$999,999,999') ||
                         ', five times your annual income.');
  else
    l_out.put('valid', true);
  end if;
  return l_out.to_clob;
exception
  when no_data_found then
    l_out.put('valid', false);
    l_out.put('message', 'I could not find that application.');
    return l_out.to_clob;
end;
/

insert into fc_connectors (connector_id, connector_type, target, description)
values ('check_affordability', 'PLSQL', 'CHECK_AFFORDABILITY', 'Amount at most 5 x income');
Payload contents

slots holds the conversation's answers (the Ask nodes). The loaded record's values are kept apart from them, so a connector that needs a record value either reads it from the table, as above, or relies on a slot that holds the key.

Validators on an Ask node work the same way, with slot set to the Ask's slot. A Submit node validates every answer again before it calls its connector.

05Who can change a field

A field is editable only when both of these are true:

  1. The registry allows it. fc_data.is_updatable returns true when the field has UPDATABLE = 'Y'. For a PLSQL source, a field with no row in FC_DATA_SOURCE_FIELDS counts as updatable, because your update function is expected to enforce the rules.
  2. Its editableWhen condition holds. The condition can read answers and the record's values.
{ "field": "amount", "label": "Amount",
  "editableWhen": { "all": [
      { "slot": "app.status", "op": "=", "value": "PENDING" },
      { "slot": "app.amount", "op": "<", "value": 1000000 } ] },
  "lockedMessage": "The amount is fixed once the application is approved." }

A locked field is shown with its lockedMessage instead of a prompt. The flow can never make a field editable that the registry doesn't allow; editableWhen can only narrow it further.

06Which rows

ROW_FILTER is trusted SQL written by an administrator. FC_DATA appends it to the search, the read after a pick, and the UPDATE, so a row outside the filter can't be found, read or changed. Two bind variables are filled by the server, never by the browser:

BindValueTypical filter
:APP_USERThe signed-in APEX userowner = :APP_USER
:FC_VERIFIEDThe value proved by a Verify step in this conversation, otherwise null (so no rows match)lower(email) = lower(:FC_VERIFIED)

Two node options build on it:

  • byRowFilter: true on Find record or Bulk update searches with the filter alone, for example "my open requests". The server refuses it for a source that has no row filter.
  • requireVerified: "email" refuses the search until the email answer has passed a Verify step with its current value.
Tip

Keep the filter to simple column comparisons with an index behind them. It runs on every search and every save.

07What Save changes does

Save changes trusts nothing that happened earlier in the conversation. In order, it:

  1. Works out the changed fields by comparing the record's current values with the values loaded from the table. With no changes it says so and takes noChanges (or saved).
  2. For each changed field, checks that the Change fields node declares it and that it is still editable. If not, it takes forbidden.
  3. Runs the field's input rules and validators again. If one fails it shows the message and asks for that field again, and the save waits.
  4. Calls fc_data.update_row with the key, the version, the original values and the changes. Only changed fields are sent.
  5. Writes an audit event with before, after and the result, then follows the port for the result.
ResultMessage shownPort
okYour message, else savedTextsaved
conflictYour message, else conflictText, else a defaultconflict, else error
forbiddenYour message, else "You're not allowed to change this record."forbidden
notfound, anything elseYour message, else "Sorry, the changes could not be saved."error
Connect every port

If the port for a result isn't connected, the conversation ends as failed. Give each Save changes node at least saved, conflict, forbidden and error.

08Concurrent edits

FC_DATA uses optimistic locking, so a row is never held locked while a user is thinking.

  • With a VERSION_COLUMN, the update adds and to_char(t.row_version) = :ver and sets row_version = row_version + 1.
  • Without one, it requires every changed column to still hold the value that was loaded, using decode so nulls compare as equal.

When no row is updated, FC_DATA reads the row again. If it is gone (or the row filter now hides it) the result is notfound; otherwise it is conflict. On a conflict the engine reloads the latest values, puts the user's edits on top, and takes the conflict port. Route that port back to your summary so the user can review the merged record before saving again.

An update that matches more than one row raises -20043, because KEY_COLUMN must be unique.

09PL/SQL data sources

When saving a change means more than one UPDATE (several tables, approvals, workflow state, rules that need a lot of data), register the source as PLSQL. You write three functions with the connector signature, function f(p_payload in clob) return clob, and FC_DATA calls them in place of its own SQL.

insert into fc_data_sources (source_id, source_type, search_target, get_target, update_target, description)
values ('leave_req', 'PLSQL', 'LEAVE_API.SEARCH', 'LEAVE_API.GET', 'LEAVE_API.SAVE',
        'Leave requests, saved through LEAVE_API');

The update contract

Your update function receives:

{ "key": "LR-1042", "version": "7",
  "original": { "start_date": "2026-12-21" },
  "changes":  { "start_date": "2026-12-24" },
  "appUser": "JSMITH", "verified": null, "context": { … } }

and returns one of these. The flow follows the matching port and shows your message.

{ "status": "ok", "version": "8", "message": "Saved. Your manager has been told." }
{ "status": "forbidden", "message": "Leave can't start on a public holiday." }
{ "status": "conflict" }
{ "status": "notfound" }

Return the new version on success so the next save in the same conversation checks against it.

Example: LEAVE_API.SAVE

function save (p_payload in clob) return clob is
  l_in   json_object_t := json_object_t.parse(p_payload);
  l_chg  json_object_t := l_in.get_object('changes');
  l_out  json_object_t := json_object_t();
  l_row  leave_requests%rowtype;
  l_from date;
  l_to   date;

  function reply (p_status in varchar2, p_msg in varchar2 default null) return clob is
  begin
    l_out.put('status', p_status);
    if p_msg is not null then l_out.put('message', p_msg); end if;
    return l_out.to_clob;
  end;
begin
  begin
    select * into l_row from leave_requests
     where req_id = l_in.get_string('key')
       and employee = l_in.get_string('appUser')      -- your own row rule
       for update nowait;
  exception
    when no_data_found then return reply('notfound');
    when others then
      if sqlcode = -54 then return reply('conflict'); end if;   -- locked by someone else
      raise;
  end;

  if to_char(l_row.row_version) <> l_in.get_string('version') then
    return reply('conflict');
  end if;
  if l_row.status <> 'DRAFT' then
    return reply('forbidden', 'This request has been submitted. Ask your manager to return it first.');
  end if;

  l_from := case when l_chg.has('start_date') then to_date(l_chg.get_string('start_date'), 'YYYY-MM-DD') else l_row.start_date end;
  l_to   := case when l_chg.has('end_date')   then to_date(l_chg.get_string('end_date'),   'YYYY-MM-DD') else l_row.end_date   end;

  if l_to < l_from then
    return reply('forbidden', 'The last day must be on or after the first day.');
  end if;
  if holidays.is_holiday(l_from) then
    return reply('forbidden', 'Leave can''t start on a public holiday.');
  end if;
  if leave_balance(l_row.employee) < (l_to - l_from + 1) then
    return reply('forbidden', 'You don''t have enough leave left for those dates.');
  end if;

  update leave_requests
     set start_date = l_from, end_date = l_to, row_version = row_version + 1
   where req_id = l_row.req_id;

  l_out.put('version', to_char(l_row.row_version + 1));
  return reply('ok', 'Saved. Your new dates are ' || to_char(l_from, 'DD Mon') ||
                     ' to ' || to_char(l_to, 'DD Mon') || '.');
end save;
Why return a status instead of raising

A returned forbidden shows your exact message and takes the forbidden port, and the conversation carries on. A raised exception rolls back the whole turn (see the next section). Raise only for real faults.

Don't commit inside these functions. Each turn runs under the savepoint fc_turn, and APEX commits when the request ends.

10Constraints and triggers

FC_DATA runs an ordinary UPDATE with bind variables, so check constraints, foreign keys, unique keys and triggers all apply. They are the last line of defence and the only one that also covers changes made outside FlowChat.

create or replace trigger loan_app_bu
before update of amount on loan_applications for each row
begin
  if :old.status <> 'PENDING' then
    raise_application_error(-20001, 'The amount is fixed once the application is approved.');
  end if;
end;
/

What the user sees

Save changes sets the savepoint fc_save before it calls fc_data.update_row. When the update raises (a trigger, a constraint, a PLSQL source), only that save is undone, the flow takes the error port, and the conversation carries on.

  • Codes -20000 to -20999: the user sees the first line of the message without its ORA-nnnnn: prefix. For the trigger above that is "The amount is fixed once the application is approved." The ORA-06512 and ORA-04088 lines Oracle adds are dropped.
  • Any other error, such as ORA-02290 for a check constraint: "Sorry, the changes could not be saved." The details go to the APEX debug log.

The audit event records "result": "error" and the message. Errors raised anywhere else in a turn still roll back the whole turn to fc_turn and keep the conversation on the same step, with the same first-line message.

Give constraints a friendly twin

A check constraint's own message isn't readable by customers. For a rule a user can break, also raise it from a trigger with a -20xxx code and a plain sentence, or check it in a validator or a PLSQL source, so the user meets the friendly message first.

11Bulk update

Bulk update searches a source, shows how many rows match and asks for confirmation. It then applies the same change to each row through fc_data.update_row, so the field whitelist, the row filter and the version check apply to every row.

  • Rows that return conflict, forbidden or notfound are counted as failed; the rest are saved and the flow takes partial (or done if partial isn't set).
  • maxRows (default 50, at most 500) caps the batch. More matches take tooMany.
  • set values are written as given, so check any value that comes from an answer ({"slot": …}) on the Ask node that collects it.
  • Each row is updated under its own savepoint, fc_bulk_row. A row whose update raises (a trigger, a constraint) is undone and counted as failed, and the other rows are still saved.
  • The first failure message, from a -20xxx error or a PLSQL source's message, is added to the default partial text. A custom prompts.partial can place it with {{failReason}}.
  • The audit event lists the key, result and message of up to 20 failed rows.
"prompts": { "partial": "Closed {{updated}} of {{count}}. {{failed}} were skipped, for example: {{failReason}}" }

13Audit and debugging

Every save writes an OUT event to FC_EVENTS for the Save changes node, with the source, key, values before and after, and the result:

{ "action": "update", "source": "loan_app", "key": "LA-2291",
  "before": { "amount": 200000 }, "after": { "amount": 250000 }, "result": "ok" }
-- saves that were refused in the last 7 days
select e.session_id, e.node_id, e.created_at,
       json_value(e.payload, '$.key')    as record_key,
       json_value(e.payload, '$.result') as result
  from fc_events e
 where e.direction = 'OUT'
   and json_value(e.payload, '$.action') = 'update'
   and json_value(e.payload, '$.result') <> 'ok'
   and e.created_at > systimestamp - interval '7' day
 order by e.created_at desc;

Fields marked pii are masked in the transcript. When a turn fails with an exception and the conversation is being debugged, a DBG event with the error message is written after the rollback.

The designer's Test tab runs the flow in the browser against sample data, which is enough to check routing and messages. Test business rules in the database itself, through the APEX page that hosts the chat widget.

14Release checklist

  • Only the fields users should change have UPDATABLE = 'Y'.
  • The source has a ROW_FILTER using :APP_USER or :FC_VERIFIED, unless every user may see every row.
  • The source has a VERSION_COLUMN, or you accept the original-values check.
  • Each changed field has input rules, and cross-field rules have a server validator.
  • State-dependent fields have editableWhen and a lockedMessage.
  • Save changes connects saved, conflict, forbidden and error, and conflict leads back to a summary.
  • PLSQL sources return forbidden with a message rather than raising, return the new version, and never commit.
  • Triggers raise codes between -20000 and -20999 with a sentence a customer can read.
  • Test a refused save, a conflict (edit the row in SQL Developer mid-conversation) and a row outside the filter.
